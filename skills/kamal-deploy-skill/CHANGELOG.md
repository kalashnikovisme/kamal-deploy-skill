# Changelog

## 1.6.0 — 2026-10-22

Ships secret generation as an actual, reusable, executable capability instead of only documented behavior, so applying the Skill no longer requires an agent to reinvent `bin/secrets generate` from prose.

- **New reusable implementation**: `templates/bin/secrets` - a self-contained, installable bash script implementing `check`, `edit`, `show`, `policy` (`generate --list`), `generate <NAME>`, `generate --missing`, and `rotate <NAME>`, dispatched through a generator registry (`policy -> generator -> generated primitive(s) -> backend adapter`) rather than a single generic CSPRNG call applied to every secret.
- **New project policy file**: `config/secret-generation.yml`, generated per project from actual usage inspection (never copied from the shipped template verbatim). Contains only `policy`/`generator`/`bytes`/key-pair component names - no secret values - and is safe to commit. Template at `templates/config/secret-generation.yml`.
- **Generator functions**: `random_symmetric_key`, `random_password`, `random_token` (CSPRNG-backed, policy-defined entropy, never a hardcoded universal size) and `vapid_key_pair` (real EC P-256 key-pair generation via `openssl`, routing the private component to the secret backend and the public component to clear configuration).
- **Zero-argv-exposure SOPS writes**: generated values are piped through `jq --rawfile .../dev/stdin` and never appear as a literal command-line argument, in `ps`, in a temp file, or in command output; writes go through a decrypt → in-memory merge → re-encrypt cycle with no persistent plaintext file.
- **Refusal semantics enforced by the script, not just prose**: refuses to generate over an existing real value (that's rotation, exposed separately via `bin/secrets rotate <NAME>` with interactive confirmation - `generate` itself has no overwrite flag); refuses `existing_value_must_be_preserved` even when the backend currently holds only a placeholder; refuses `provider_managed` with a pointer to the real provider; refuses any name with no recognized policy entry (`GENERATION_POLICY_UNKNOWN`) rather than falling back to a generic random string.
- **`generate --missing`**: generates only primitives whose policy positively permits local generation and that are currently missing/placeholder; reports already-present, provider-managed, preserve-only, and unknown-policy secrets by name with the skip reason, including backend keys that have no policy entry at all.
- **Derived-value integration preserved**: generating `POSTGRES_PASSWORD` never stores `DATABASE_URL` independently; validation confirms the derived value still resolves.
- **Executable regression tests**: `tests/secret-generation/run_tests.sh` builds a throwaway SOPS + age project and exercises the shipped script end-to-end (fresh HMAC JWT secret, existing-value refusal, preserve-only refusal, provider-managed refusal, unknown-secret refusal, PostgreSQL password plus derived-value integrity, `--missing` selective generation, simulated storage failure, VAPID key-pair generation and routing, special-character password encoding, and a leak sweep across command output and `git diff`) - skips cleanly if `sops`/`age-keygen`/`jq`/`openssl` are unavailable, mirroring `bin/secrets check`'s own `SKIP` convention.
- Updated `agents/patterns/secret-generation.md` with "The reusable `bin/secrets` implementation" section (generator registry, policy-file format, supported commands, how the Skill installs/merges it into a project without overwriting an existing `bin/secrets`); updated `agents/patterns/secrets-sops-age.md`'s developer-UX section to point at the concrete templates; updated `SKILL.md`'s Step 4b to install/merge the helper whenever a SOPS + age backend is configured or already established.

## 1.5.0 — 2026-10-21

Adds first-class, standards-aware secret primitive generation and secure storage, so the Skill can mint a credential correctly instead of leaving a placeholder or inventing a value.

- **New core invariant**: the model may decide *how* a secret should be generated, but must never generate cryptographic secret material itself - generation always comes from a trusted CSPRNG or protocol-specific tool (`openssl rand`, the OS CSPRNG, Ruby `SecureRandom`, Python `secrets`, Node `crypto`, Go `crypto/rand`, `ssh-keygen`, `age-keygen`, a VAPID-library's own key-pair generator, etc.) and is written directly into the configured secrets backend - never printed in a report, chat message, log, commit message, or temp file. Added `agents/patterns/secret-generation.md`, the dedicated pattern covering this end to end.
- **Generation-policy model**: every secret primitive is classified as `LOCAL_GENERATABLE`, `PROTOCOL_GENERATABLE`, `FRAMEWORK_GENERATABLE`, `INFRASTRUCTURE_GENERATABLE`, `PROVIDER_MANAGED`, `EXISTING_VALUE_MUST_BE_PRESERVED`, or `GENERATION_POLICY_UNKNOWN` from actual usage inspection (application code, library/framework config, validation rules) - never from the variable name alone. Only the first four may ever be generated automatically; provider-managed credentials are always rejected with a pointer to the real provider, and unknown secrets are never guessed at.
- **Standards-aware generation by category**: random application secrets (JWT HMAC/session/CSRF/cookie-signing) are sized to the actual algorithm in use, not a universal length; passwords are generated at full CSPRNG entropy and only percent-encoded later when embedded in a derived URI, never weakened to simplify encoding; asymmetric key pairs (RSA/EC/Ed25519/SSH/VAPID) are generated with correct protocol tooling, never as two independent random strings, with private/public components classified independently.
- **Existing value vs. rotation**: generating over a real existing value is never silent - it's treated as a rotation requiring explicit user intent, with a new generalized 12-step rotation workflow (identify consumers/derived values/external systems, determine grace-period and user/session impact, obtain explicit intent, generate, update backend and controlled external systems, validate, retire old credential only once safe).
- **Atomic generation principle**: generate → persist → validate → report is one operation; a storage failure is a failed generation, never papered over by displaying the value as a fallback.
- **Backend-specific write strategies**: added SOPS + age single-value update guidance (avoid a full plaintext round-trip to disk, avoid exposing the value via command arguments, validate by internal decrypt-and-check without printing) and 1Password guidance (write via its own item/field API, never switch backends merely because generation is easier elsewhere); a backend with no safe write path is reported as unable to auto-generate rather than generating into memory only.
- **`bin/secrets generate <NAME>` / `bin/secrets generate --missing`**: extends the existing SOPS developer-UX shape (`agents/patterns/secrets-sops-age.md`) with generation, restricted to positively classified, currently-missing/placeholder, locally-generatable primitives - never provider-managed or unknown names, never an existing real value.
- **Derived-value integration**: generating a primitive (e.g. `POSTGRES_PASSWORD`) never also stores its derived composite (`DATABASE_URL`); post-generation validation re-confirms the derived value still resolves and its URI encoding still succeeds, per `agents/patterns/derived-deployment-values.md`, which now cross-references this new pattern instead of duplicating condensed generation guidance.
- **Validation and audit trail**: added a non-printing post-generation validation checklist (presence, non-emptiness, placeholder gone, format/entropy match, pair-relationship correctness, derived values still resolve, no accidental clear/`NEXT_PUBLIC_*` exposure) and a fixed report format (status/method/backend/stored/validation - never the value).
- Updated `agents/patterns/secrets-backend.md` and `agents/patterns/secrets-sops-age.md` to cross-reference the new pattern for generation and for the generalized rotation workflow. Updated `SKILL.md`'s Secrets Policy with a new rule 7 stating the core invariant, and Step 4b with a load point before generating any primitive's value.
- Added `tests/fixtures/secret-generation/EXPECTED.md` covering missing/existing JWT secrets, provider-managed rejection, fresh PostgreSQL password plus derived-value integrity, VAPID key-pair classification, unknown-secret rejection, `--missing` selective generation, storage-failure handling, SOPS end-to-end generation, special-character password encoding, and asymmetric-signing key-pair generation - no fixture contains real secret material.

## 1.4.0 — 2026-10-21

Adds a generalized derived-deployment-values model so the Skill stops treating deterministic connection strings as independent secrets.

- **New core invariant**: never ask the user for a deployment value the Skill can derive deterministically from its own Kamal/accessory configuration plus already-stored secret primitives; store secret primitives, not duplicated derived representations of them. Added `agents/patterns/derived-deployment-values.md`, defining four value categories (secret primitive, derived secret value, derived clear configuration, user-supplied clear/public configuration), a mandatory dependency-analysis step run before any connection-string secret or placeholder is written, and the precedence rule that Kamal topology is the source of truth for hosts/ports/names while the secrets backend is the source of truth for primitives.
- **PostgreSQL**: `DATABASE_URL` for a Skill-managed accessory is now derived at secret-resolution time from `POSTGRES_PASSWORD` plus accessory topology, never stored as an independent secret. Requires correct percent-encoding of the password component (not a weak-character-set workaround) so passwords containing `@ : / ? # %` can't break the URL.
- **Redis**: an unauthenticated accessory's `REDIS_URL` is now generated as derived *clear* configuration (no secret material, never enters the secrets backend, never becomes a placeholder); an authenticated accessory stores only `REDIS_PASSWORD` as the primitive and derives `REDIS_URL` the same way as `DATABASE_URL`.
- **External/provider-managed databases are explicitly exempted**: a `DATABASE_URL` pointing at Supabase/Neon/RDS/etc. - anything whose topology the Skill doesn't control - is stored as a single opaque secret primitive and never decomposed or reconstructed. Existing production connection strings are never swapped for a newly-derived accessory URL without the user's explicit migration confirmation.
- **Secret generation**: the Skill may now generate a brand-new primitive (e.g. a new accessory's password) with cryptographically secure randomness when it owns both sides of that credential and there's no existing value to preserve - never for third-party credentials, never regenerating an existing one, never printed anywhere.
- **Placeholder policy**: `TODO_FILL_IN` may only be written after confirming the value isn't derivable from topology, derivable from topology plus a primitive, or safely Skill-generatable.
- Fixed a latent bug in `examples/with-postgres.md`: `DATABASE_URL` was previously placed in `env.clear` with shell-style `${POSTGRES_PASSWORD}` interpolation, which `deploy.yml`'s YAML/ERB parsing would never expand - it is now correctly derived in `.kamal/secrets` and listed under `env.secret`. Extended `examples/with-redis.md` with an authenticated-accessory variant.
- Updated `agents/patterns/secrets-sops-age.md` and `agents/patterns/secrets-backend.md` to apply the same derived-value rule across every backend (SOPS + age, 1Password, others), and updated `bin/secrets check` guidance so a derived value is validated via its dependencies rather than requiring its own backend entry.
- Updated `SKILL.md` Step 4b #6 to load the new pattern before any accessory connection-string secret is written, and updated the Secrets Policy section (gitignore default + the new derivation invariant).
- Added `tests/fixtures/derived-deployment-values/EXPECTED.md`, covering Skill-managed PostgreSQL (primitive + derived URL, correct encoding), unauthenticated and authenticated Redis, external PostgreSQL (no decomposition), newly-generated vs. preserved existing passwords, URI-special-character passwords, duplicated-derived-secret detection/normalization, and a derived internal service URL.

## 1.3.0 — 2026-10-21

Adds first-class support for SOPS + age as a secrets-management backend, alongside a new mandatory backend-selection step that runs before any production secret is generated.

- **New mandatory step: secrets backend selection.** Added `agents/patterns/secrets-backend.md`, loaded at the start of SKILL.md Step 4b. Before writing any production secret, it inspects the repo for an already-established backend (Rails credentials, existing SOPS, 1Password, Doppler, Bitwarden, a cloud secret manager) and preserves it - a backend is never migrated merely because another option exists, only on an explicit user request. Only when no backend is established yet does it present options (at minimum 1Password and SOPS + age) without declaring either universally more secure - they differ in ownership model, not security tier. The chosen backend is recorded in the project's own deployment documentation so future Skill invocations detect and reuse it instead of re-asking.
- States explicitly, based on Kamal's documented `.kamal/secrets`/`secrets_path`/`secrets-common` mechanics, that SOPS has **no native `kamal secrets fetch --adapter` provider** - it is integrated like any other non-native backend, via command substitution inside `.kamal/secrets` calling `sops` directly. 1Password remains the only backend covered here with a native Kamal adapter.
- Added `agents/patterns/secrets-sops-age.md`, a dedicated pattern covering: the conceptual model (encrypted config in Git + decryption key outside Git, analogous to Rails `credentials.yml.enc`/`master.key` but not a literal port); `.sops.yaml`/encrypted-file/`.kamal/secrets` repository layout and which parts may vs. must never be committed (including the per-line judgment rule for whether a committed `.kamal/secrets` is safe - only if every line is command substitution with no literal value); Kamal integration via `sops --extract` command substitution with fail-closed behavior (`set -e`), no decrypted file left on disk, and no secret printed during normal deployment; `bin/secrets edit`/`show`/`check` developer UX plus the raw underlying `sops` commands; initial setup for a brand-new age identity and reuse of an existing one, with no private-key exposure in chat, shell history, or commits; multi-developer recipient management via `sops updatekeys` (explicitly not a shared single identity for a team); key-loss/recovery guidance (recommend, never auto-create, a backup recovery path); the distinction between encryption-key rotation (who can decrypt) and application-secret rotation (the actual credential values) - removing a recipient does not retroactively rotate secrets they already saw; secret classification (only genuine secrets go in SOPS, not clear config); preservation of the existing `NEXT_PUBLIC_*` browser-exposure rule; a 10-step safe migration path from plaintext `.kamal/secrets` with git-history compromise handling; and a pre-deployment validation checklist that explicitly excludes `kamal secrets print`/full `sops -d` dumps as routine validation.
- Updated `CLAUDE.md`/`AGENTS.md`'s secrets rule: `.kamal/secrets` is gitignored by default, but may be committed when every line resolves via command substitution from a committed encrypted backend with no literal secret value present.
- Updated `README.md` with a secrets-backend comparison table (Rails credentials / 1Password / SOPS + age: storage, decryption/access, best fit, native-Kamal-adapter status) and a new "What it does" bullet describing the backend-detection step.
- Added `tests/fixtures/secrets-backend/EXPECTED.md` covering: no established backend (Case A); SOPS + age selected from scratch (Case B); existing 1Password preserved (Case C); existing Rails credentials preserved (Case D); existing SOPS conventions preserved (Case E); safe migration from plaintext `.kamal/secrets` with git-history compromise handling (Case F); an age private identity found inside the repo treated as a security blocker (Case G); a missing age identity at deploy time failing closed (Case H); and `NEXT_PUBLIC_*` isolation preserved under SOPS + age (Case I).

## 1.2.0 — 2026-10-21

Fixes a topology-level design flaw found during real-project use: the Skill tended to map each discovered Deployable Unit to its own independent Kamal deployment (`config/deploy.<unit>.yml` per unit) by default, even when the units belonged to one product running on one server and had no actual reason to be separate Kamal configurations.

- **New core invariant: Deployable Unit ≠ Kamal Deployment.** Added `agents/patterns/deployment-boundary.md`, a new mandatory step that runs after Deployable Unit discovery/selection and before stack detection whenever the Kamal-managed subset has more than one unit. It introduces four distinct concepts - Deployable Unit, Runtime Unit, Kamal Role, Accessory, Kamal Deployment - and a three-level decision hierarchy: (1) one application image with roles (preferred default when units share a product/infrastructure/release cadence), (2) primary application + accessories (for components that genuinely fit accessory lifecycle, evaluated explicitly rather than assumed), (3) multiple independent Kamal deployments (only for a stated, concrete reason - different server fleets, independent release lifecycles, incompatible builds, different infra ownership - never merely because multiple directories/Dockerfiles/frameworks exist).
- Verified against Kamal's current configuration schema and documented explicitly: roles under `servers:` share one release image and get normal rolling zero-downtime deploys; accessories have their own image/lifecycle, are not touched by `kamal deploy`, and **cannot be routed by `kamal-proxy`** (no `proxy:` key in the accessory schema) - a component needing HTTP routing through `kamal-proxy` cannot be modeled as an accessory for that purpose, full stop.
- Added explicit guidance for same-server consolidation, frontend+backend consolidation (shared release image, `web`/`api` roles), evaluating whether a frontend's own BFF layer removes the need for a separate public backend hostname, and auxiliary application services (transcription/search/ML/etc.) requiring an explicit accessory-lifecycle evaluation instead of a default classification.
- **`agents/patterns/multi-service-repo.md` now scopes itself to units the boundary step has placed in genuinely separate ("Level 3") deployments** - it previously applied to any Kamal-managed subset with more than one unit. Added a cross-reference so its tier 1/2/3 inter-service networking model is stated to apply equally to calls between two roles of one consolidated deployment, since consolidating removes build/release/secrets duplication, not the lack of a stable Docker DNS name between role containers.
- Updated `agents/patterns/deployable-units.md` to state the new invariant at the selection step and corrected a worked example (`api/`+`worker/`) that previously implied selecting multiple units automatically triggers the multi-service pattern.
- Updated `SKILL.md` Steps 1, 2, and 5 to insert the new mandatory boundary step and to generate config as roles/accessories in one `config/deploy.yml` for consolidated units, falling back to the `config/deploy.<unit>.yml` convention only for units a Level 3 decision actually separated.
- Updated `agents/patterns/migrate-from-vercel.md` to note a migrating unit is not automatically its own Kamal deployment either - the boundary step still runs on the full Kamal-managed subset.
- Corrected `examples/multi-service-repo.md`, which previously used `api/`+`worker/` (a pair that now defaults to consolidation, see `examples/web-with-worker.md`) as its motivating example without qualification - it now states explicitly that this layout applies only once a genuine Level 3 reason has been identified, and names example reasons.
- Added `tests/fixtures/deployment-boundary/EXPECTED.md` covering: the default consolidation case (frontend+API as one application with roles, Postgres/Redis as accessories), an auxiliary service classified as an accessory after an explicit lifecycle evaluation, the same auxiliary service instead requiring zero-downtime rolling deploys (must not be silently forced into accessory lifecycle), and a genuine Level 3 split with a stated concrete reason.
- Corrected `tests/fixtures/multi-deployable-unit/EXPECTED.md`'s "both units Kamal-managed" variant, which previously expected the `-c`/`--config-file` multi-service layout directly for two same-product, same-server units with no stated separation reason - it now expects the boundary step to run first and propose consolidation into one deployment with roles, while keeping the existing hostname/networking-tier regression expectations (still valid regardless of which side of the boundary decision the units land on).

## 1.1.6 — 2026-10-21

Refines the tier 3 "stop for an explicit architectural decision" path from 1.1.5 with a resolution route that doesn't require relaxing the user's stated requirement outright.

- **Distinguish network-level internal-only from application-level private** in `agents/patterns/multi-service-repo.md`'s tier 3 section: "B must not be reachable from the public Internet at all" is a different, stronger requirement than "B may be reachable through `kamal-proxy`, but its functional endpoints must reject unauthorized external callers." Kamal can't provide the former for an application role via `kamal-proxy` alone (per tier 2's default port-publishing behavior), but it can support the latter without a second reverse proxy.
- Tier 3's presented options now lead with accepting application-level privacy (instead of only "relax the requirement" or an unspecified architecture change) as a first-class, Kamal-native resolution, still **only** when the user explicitly approves it - the agent must never substitute application-level privacy for a previously stated network-level internal-only requirement on its own judgment.
- Added concrete server-to-server authentication requirements once application-level privacy is accepted: credentials stay server-side and out of `NEXT_PUBLIC_*`/browser bundles, every sensitive functional endpoint authenticates callers, health/readiness endpoints may stay open for `kamal-proxy` health checks, use a secret/token/HMAC mechanism appropriate to the stack, and store the credential through the normal Kamal secrets mechanism (`.kamal/secrets`) - never hardcoded.
- Updated the generation gate's `REQUIRED EXPOSURE` field to distinguish `network-level internal-only` from `application-level private, approved`.
- Added a fixture sub-variant to `tests/fixtures/multi-deployable-unit/EXPECTED.md` covering the user explicitly accepting application-level privacy after a tier 3 stop: the agent must not assume this outcome unprompted, must add the required authentication rather than treating approval as removing the need for any protection, and must still never reach for Traefik/nginx/Caddy/HAProxy.
- No change to tiers 1-2 or the kamal-proxy-only architectural constraint from 1.1.5; this release only adds a resolution path within tier 3.

## 1.1.5 — 2026-10-21

Closes out the networking policy work from 1.1.4 with an explicit architectural constraint, after a real-project validation pass considered (and correctly rejected) introducing a second ingress proxy in front of `kamal-proxy` to get "true" internal-only routing.

- **Architectural constraint: `kamal-proxy` is the only reverse proxy this Skill generates or depends on.** Verified that Kamal 2 replaced Traefik with `kamal-proxy`, and that `proxy.run.publish: false` plus a second ingress (historically Traefik, per `kamal-deploy.org/docs/upgrading/continuing-to-use-traefik/`) is a documented *upgrade-compatibility* path for pre-existing Traefik users, not a target architecture - and that it's host-global configuration affecting every Kamal-managed unit on a host, not scoped to the one unit that "needs" it. Added this constraint explicitly to `agents/patterns/multi-service-repo.md` and `SKILL.md` Step 4b #8: never introduce Traefik, nginx, Caddy, HAProxy, or any other ingress/reverse-proxy layer to solve app-to-app discovery, even to satisfy an internal-only requirement.
- Collapsed the four-level hierarchy from 1.1.4 into three tiers, matching the simpler supported reality: (1) a stable native internal mechanism when one genuinely exists (in practice, only Kamal accessories), (2) `kamal-proxy` routing for HTTP(S) traffic - same-host internal Docker-network route when available, its public `proxy.host` listener otherwise, both being the same underlying mechanism and neither being a defect to flag, (3) stop for an explicit architectural decision only when the user has stated a destination must be inaccessible from the Internet and `kamal-proxy` can't satisfy that.
- **Fix: a same-host internal `kamal-proxy` route does not, by itself, satisfy an internal-only exposure requirement.** `kamal-proxy` publishes ports 80/443 to the host by default; once a unit's `proxy.host` is registered with it, that route is reachable through `kamal-proxy`'s public listener regardless of which path a same-host caller happens to use for its own request. 1.1.4's tier-3 example implied that restructuring a dependency to speak HTTP(S) (so `kamal-proxy` could route it) resolved an internal-only conflict - it doesn't, since this Skill doesn't generate the unpublish-plus-second-ingress architecture that would be needed to actually enforce that boundary. Corrected `agents/patterns/multi-service-repo.md`'s tier 2/3 text and the generation gate to state this explicitly, and added a fixture sub-variant (HTTP call + stated internal-only requirement) covering the case where tier 2 is technically available but still doesn't satisfy the requirement, so the stop at tier 3 still applies.
- Extended `tests/fixtures/multi-deployable-unit/EXPECTED.md`'s cross-unit networking variant: added checks that no agent introduces Traefik/nginx/Caddy/HAProxy as a "fix" for either the same-host HTTP case or either internal-only sub-variant (non-HTTP and HTTP), and renumbered the existing Level references to the new tier numbering.
- Updated `agents/patterns/migrate-from-vercel.md`'s topology note to the three-tier model; "switching to the internal route" and "staying on the public route" are both neutral outcomes of running the gate, not an automatic improvement or a regression to record before the gate has run.
- Preserved unchanged: the accessory-reachability guidance (`<service>-postgres`/`<service>-redis`), the absolute ban on guessed (`api-web-1`) and bare (`api`/`stt`) application-role hostnames from 1.1.4, and the generation gate's blocking behavior for unverified endpoints.

## 1.1.4 — 2026-10-21

Corrects a conceptual bug in the 1.1.2/1.1.3 networking policy, exposed by a real-project blind test: the Skill generated an application-role URL conceptually equivalent to `http://stt:3002`, reasoning (implicitly) that both containers sharing the `kamal` Docker network made that hostname valid. Re-verified against Kamal/Docker documentation and source (`lib/kamal/configuration/role.rb`, `lib/kamal/configuration/accessory.rb`, `lib/kamal/configuration/proxy/boot.rb`, and GitHub issue basecamp/kamal#1713 confirming `--network-alias` does not apply to the default `kamal` network for app roles).

- Fix: **shared `kamal` Docker network membership was never, by itself, stable application-role service discovery** - that was always true, but 1.1.2/1.1.3's existing Level-1 "`kamal-proxy` route" guidance didn't explicitly rule out the bare-hostname form (`http://<service>:<port>`) the way it already ruled out the guessed-versioned form (`<service>-web-1`). Someone reasoning from "both containers are on the same network" alone could still land on `stt:3002`. Added an explicit "Core principle" statement to `agents/patterns/multi-service-repo.md` and restated the app-container-naming verification to cover both forms symmetrically: neither a guessed versioned name nor a bare unversioned name is ever valid for an application-role target, full stop - only `kamal-proxy` itself has a stable, unversioned identity on that network. Accessories remain the one deliberate exception (their `service_name` genuinely is stable) and that guidance is unchanged.
- Changed the decision model from "internal preferred, otherwise public" to "does a stable supported endpoint exist for this call, and only then pick where it lives" - renamed and reorganized the existing three tiers into four explicit levels in `agents/patterns/multi-service-repo.md`: Level 1 stable internal routing (`kamal-proxy`, HTTP(S) only), Level 2 stable private routing (an already-configured private mechanism, never provisioned speculatively), Level 3 `kamal-proxy`/public `proxy.host` as a valid, correct fallback (not a failure) when Levels 1-2 don't produce a stable endpoint, and a new Level 4: when internal-only exposure is required and no stable endpoint exists, STOP and present the architectural choices instead of silently falling back to public routing or inventing a hostname.
- Added a mandatory "Generation gate" to `agents/patterns/multi-service-repo.md`: before generating any application-role-to-application-role URL, the Skill must answer CALLER/CALLEE/CALLER EXECUTION CONTEXT/REQUIRED EXPOSURE/ROUTING MECHANISM/STABLE ENDPOINT/WHY ENDPOINT IS STABLE/ROLLING-DEPLOY BEHAVIOR; if the endpoint or its stability justification is unverified, generation for that dependency is blocked rather than filled with a placeholder.
- Clarified that Level 1 (`kamal-proxy` Host-header routing) only applies to HTTP(S) traffic; a non-HTTP protocol (raw TCP/gRPC) must drop to Level 2, and to Level 4 if no Level 2 mechanism exists and internal-only exposure is required.
- Added an explicit `127.0.0.1`/`localhost` anti-pattern note to `agents/recipes/nextjs.md`'s server-side inter-unit guidance: these always refer to the caller's own container/process namespace, never another Deployable Unit, with or without a fallback value - the blind test also produced a server-side fallback to `127.0.0.1:3001` meaning "the API unit."
- Changed `agents/patterns/migrate-from-vercel.md`'s topology-improvement note: replacing a Vercel-era public call with an internal route is allowed only when the generation gate actually establishes a stable Level 1/2 endpoint for that call - "remove the public hop" is no longer stated as an automatic improvement to record before the gate has run.
- Extended `SKILL.md` Step 4b #8 to reflect the corrected decision model and explicitly name the bare-hostname anti-pattern alongside the existing guessed-hostname one.
- Extended regression protection in `tests/fixtures/multi-deployable-unit/EXPECTED.md`: the existing cross-unit networking variant now also rejects a bare `http://api:<port>` hostname (not just guessed/versioned ones) and expects the generation gate's fields to be articulable for the chosen route; added a new sub-variant covering a non-HTTP protocol between app-role services where internal-only exposure is required and no Level 2 mechanism exists - expected behavior is Level 4 (stop and present the decision), not a silent Level 3 fallback or an invented hostname.

## 1.1.3 — 2026-10-20

Changes the default inter-service networking policy introduced in 1.1.2, based on deeper verification against Kamal's source (`lib/kamal/commands/{docker,app,proxy,accessory}.rb`, `lib/kamal/configuration/proxy/boot.rb` in basecamp/kamal).

- Verified: `kamal setup` creates one Docker network per host (literally named `kamal`); every app, accessory, and proxy container on that host joins it regardless of which `deploy.yml`/`service:` they belong to. App containers are named with a version suffix that rotates every deploy (not a stable DNS target); accessory containers keep a stable, non-versioned `service_name`; the single per-host `kamal-proxy` container has a permanently fixed name (`"kamal-proxy"`, never versioned) and already tracks each service's current live container by `Host` header, for any caller on that network.
- Fix: 1.1.2's "Inter-service communication" policy defaulted same-host service-to-service calls to the public `proxy.host`/HTTPS route merely because it was the easiest stable thing to point at. Replaced the default with a three-tier policy - same-host internal (call through the local `kamal-proxy` container over the `kamal` Docker network, `Host` header set to the target's `proxy.host`), different-host private networking (prefer an existing/provisioned private path over the public internet), then public `proxy.host`/HTTPS as an explicit fallback with a stated reason. The existing rule against guessing a target's app-container name (`<service>-web-1`, etc.) is unchanged and still absolute - the fix is about *not* reaching for the public route by default, not about weakening that rule.
- Add the exposure/communication split to `agents/patterns/multi-service-repo.md` and SKILL.md Step 4b #8: whether a unit is publicly reachable and how a given caller reaches it are independent per-unit, per-caller decisions - a unit with a public webhook endpoint does not mean other internal callers should use that public endpoint instead of the internal route.
